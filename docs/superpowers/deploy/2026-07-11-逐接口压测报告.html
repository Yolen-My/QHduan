⚠️ 诚实说明(先看这个)
这次压测比之前更严格、更真实,暴露了区分度:走 Redis 缓存的客户端接口(/api/state、/api/questions)和写入(注册/提交)在 1000 并发下表现优秀;但直连 PocketBase 的旧架构接口(/pb/ranking-data、/pb 题库直查)和整页 SSR 在极限并发下会吃力。关键在于:前者是客户端真实高频用的,后者不是。下面每个接口的数字都标注了它是否在客户端热路径上。

① 测试方法(为何有的数字很高)

  • 压测机 txy 跨互联网打生产公网 IP,经完整入口 nginx → 前端/网关/PocketBase。
  • 三组独立测试:A 客户端热路径混合(读缓存+WS);B 全接口逐个打标签(含直连 PB + 整页);C 隔离写入。
  • B 组用 constant-vus 无思考时间连续猛打,比真实用户(点一下歇几秒)激进得多;且 B 组自身写入把 players 灌到了 8893 条,让 ranking-data 的全表扫描越来越慢(真实活动最多 ~1000 人)。
  • 热路径 = 客户端真实高频调用;非热路径 = 旧架构遗留接口,我的客户端不用(改走 WS/Redis)。

⑤ 诚实结论

✅ 客户端真实用到的接口,全部扛住 1000 并发
排行/游戏状态(/api/state,走 Redis)、题库(/api/questions,走 Redis)、WebSocket 推送、注册、提交——这些是活动当天客户端高频调用的接口,在 1000 并发下 p95 均 <1 秒、失败率 <0.3%。

⚠️ 需知晓的两个真实弱点

  • 直连 PocketBase 的接口(/pb/ranking-data 等)不抗高并发直连——SQLite 单进程瓶颈。但我的架构里客户端不直接高频调用它们(排行走 WS/Redis)。仅在被压测机直接猛打时暴露,不是活动风险。
  • 整页 SSR(首页/大屏)在极端连续猛打下变慢(p95 13s)——但真实用户每页只加载一次,之后靠 WS/API 交互。开场 1000 人分散加载(≈17 页/秒)没问题;若担心开场瞬时齐涌,可给整页加 nginx 静态缓存进一步加固。
